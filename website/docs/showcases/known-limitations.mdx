# Known limitations & roadmap

Every other page in this section shows something real and working. This page is the deliberately honest
counterpart: what's declared in the API but doesn't do what its name implies, tracked as real GitHub issues
rather than swept under the rug. It exists to serve two purposes — confirming what's actually safe to rely on
today, and seeding ideas for what to build next.

## Most of `TableConfig.features` is a consumer hint, not an enforced feature

`TableConfig.features` declares ten boolean flags: `search`, `filter`, `pagination`, `columnVisibility`,
`csvExport`, `rowSelection`, `viewToggle`, `floatingBar`, `advancedFilter`, `sorting`. Only two of them are
read anywhere in the library's own code, and only for a dev-mode console warning (`advancedFilter` enabled
while `filter` is disabled) — not to actually disable anything.

The [config cascade showcase](./config-cascade) demonstrates the practical consequence directly: setting
`features.sorting: false` doesn't stop `useTableCraft` from wiring up full sorting — the demo's own
`SortableDataTable` component has to read `config.features.sorting` itself and choose whether to render a sort
button at all. Every other flag in this list works the same way, or would if a consumer wired it up the same
way: they're hints for your own UI to read via `useTableConfig()`, not switches the library flips for you.

Tracked in [#42](https://github.com/elsieej/another-table-craft/issues/42).

## `ResolvedTableConfigContext` is never reachable in real usage

`useTableConfig()` and `useTableTranslations()` are documented as seeing the fully-resolved config (all four
cascade layers, including instance-level overrides) when called "inside a `useTableCraft` render tree." In
practice, that path is structurally unreachable: `useTableCraft` is a hook, not a component, so it has no JSX
children to wrap in a context provider. The only place `ResolvedTableConfigContext.Provider` is ever rendered
in this codebase is a test helper.

The consequence, demonstrated directly in the [i18n & RTL showcase](./i18n-rtl): passing `translationFn` or
`direction` as **instance-level** `config` to `useTableCraft` is invisible to `useTableTranslations()`/
`useTableConfig()` called anywhere else — only `TableProvider` (which does establish a real context) actually
reaches them. Every showcase on this site that needed provider-visible config used `TableProvider` for exactly
this reason.

Tracked in [#41](https://github.com/elsieej/another-table-craft/issues/41).

## `TableConfig.pagination`/`search`/`filter` aren't wired into the default store

`useTableCraft`'s default store construction calls `createUrlStateStore()` with **no arguments** — even though
`config.pagination.defaultPageSize`, `config.search.debounceMs`, and `config.filter.defaultSerializer` share
the exact same names as `createUrlStateStore`'s own `defaultPageSize`, `debounceMs`, and `defaultSerializer`
options. Setting any of these on `TableConfig` has no effect on a table's actual behavior; every showcase on
this site that needed to demonstrate a non-default page size or serializer had to read the value back out of
`config` and pass it into its own store construction by hand — the same workaround a real consumer would need
today.

Tracked in [#59](https://github.com/elsieej/another-table-craft/issues/59).

## `createCsvConfig` hardcodes the CSV delimiter

The [CSV export custom config showcase](./csv-export-custom-config) covers this one directly: the underlying
`export-to-csv` package supports a configurable `fieldSeparator`, but `createCsvConfig` hardcodes it to `,` and
never exposes it through `CsvExportOptions`. There's currently no way to get a semicolon- or tab-separated
export without bypassing this library's CSV helpers entirely.

Tracked in [#58](https://github.com/elsieej/another-table-craft/issues/58).

## Ideas for next

Distinct from the gaps above — not filed issues yet, just things this initiative surfaced as plausible next
steps:

- **Export the Base UI presentation primitives.** `components/ui/` holds a full set of table-adjacent
  components (button, card, table, dropdown menu, and more), but none of them are exported through the
  package's public API today — only the headless core is. A consumer who wants this library's actual look and
  feel, not just its state management, currently can't get it from the package itself.
- **A documented pattern for persisting row selection.** `TableStateSnapshot` deliberately excludes row
  selection as ephemeral UI state (a deliberate, correct design choice) — but that leaves "how do I keep a
  user's selection across a page reload if I actually want to" entirely unanswered. A short recipe, not
  necessarily a code change, would close that gap.
- **Broader `export-to-csv` option pass-through.** Once `fieldSeparator` lands (#58), the same option-passing
  gap likely applies to other real `export-to-csv` options this library doesn't expose yet — `quoteStrings`,
  `showColumnHeaders`, `columnHeaders`, and a few others.
