# Config cascade

Table config resolves through four layers, each able to override the one before it:

1. **Defaults** — `DEFAULT_TABLE_CONFIG`, baked into the library.
2. **Provider** — whatever a `<TableProvider config={...}>` ancestor sets.
3. **Instance** — the `config` option passed to a specific `useTableCraft` call.
4. **Plugins** — `TablePlugin`s registered on the config, applied in priority order (its own showcase).

Each layer only needs to set the fields it cares about; anything it doesn't touch falls through to the layer
below.

<ConfigCascadeExample />

All three tables above share the same 12 rows. Table 1 has no `TableProvider` ancestor and no instance
config, so it resolves straight to the library's defaults (`pageSizeOptions: [10, 20, 30, 40, 50]`,
`defaultPageSize: 10`). Tables 2 and 3 both sit inside one `<TableProvider config={{ pagination: {
pageSizeOptions: [3, 6, 9], defaultPageSize: 3 }, features: { sorting: false } }}>` — table 2 takes that as-is,
while table 3 additionally passes its own instance `config={{ pagination: { defaultPageSize: 6 } }}`. Compare
the "Resolved:" line under each table: table 3's `defaultPageSize` (6) wins over the provider's (3), while its
`pageSizeOptions` and `features.sorting` still come from the provider unchanged — an instance override only
overrides what it actually sets.

:::note
`config.pagination.defaultPageSize` does seed `useTableCraft`'s own default store now — but only when no
`store` is passed at all. Every table on this page passes its own explicit `store` (so that three different
tables, each needing a genuinely different current page size, can all be visible on this one page
simultaneously without fighting over a single default). That's why this demo still reads `defaultPageSize`
back and seeds each store manually — not because the wiring doesn't exist, but because explicit stores always
take priority over it, same as any other `store` option.
:::

## Sorting is a consumer hint, not an enforced feature

Notice tables 2 and 3 render _plain, unclickable_ column headers instead of the sort buttons in table 1. The
library itself doesn't disable sorting when `features.sorting` is `false` — `useTableCraft` always wires up
full TanStack sorting regardless of that flag. This page's own `SortableDataTable` component reads
`config.features.sorting` and renders a button-with-`aria-sort` or a plain `<span>` accordingly:

```tsx
const { table, config } = useTableCraft({ data, columns, /* ... */ })

<SortableDataTable table={table} sortable={config.features.sorting} />
```

Every flag on `TableConfig.features` works this way by design — none of them are enforced by the library
itself, `sorting` is just the one this page happens to demonstrate. Each flag's own doc comment (visible in
your editor's autocomplete, or directly in the library's `TableFeatureFlags` type) spells out exactly what it
does and doesn't do.
